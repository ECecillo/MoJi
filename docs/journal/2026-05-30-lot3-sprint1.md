# 2026-05-30 (4) — Lot 3 sprint 1 : SM-2 + ProgressRepository localStorage + bouton Réviser

## Objectif de la session

Ouvrir le Lot 3 (Système de révision, cf. RFC 0007). Premier sprint actionnable et visible côté utilisateur :

1. Algorithme SM-2 pur et testable.
2. Mapping des sessions de tracé (refusals + completed) vers une quality SM-2.
3. Persistance de la progression en local.
4. Hookup du canvas : à chaque caractère terminé, on enregistre la session.
5. Bouton **Réviser (N)** dans le header du glossaire, qui ouvre le prochain item dû.

Hors périmètre de ce sprint : backend Go + sync, UI de tableau de bord de révision, filtre "statut d'apprentissage" dans le glossaire.

## Décision structurante — déviation à la RFC 0007 sur le stockage

La RFC 0007 indique IndexedDB pour le `ProgressRepository`. **Pour ce sprint, on dévie volontairement vers `localStorage`**, pour les raisons suivantes :

- **Parité avec la RFC 0010** (surcharges de traduction) qui vient d'être actée. Même pattern : blob JSON unique sous une clé versionnée, validation au read, retombe sur vide en cas de corruption / mismatch de version.
- **Volume petit** à HSK 1 (~150 caractères × quelques octets par entrée). Limite localStorage (~5 Mo) très largement au-dessus.
- **Migration future possible via le port** `ProgressRepository` : le domaine n'importe pas l'adapter, on plug un `IndexedDBProgressRepository` quand le volume ou les besoins de query (indexes par date, sync) le justifient.
- **Pas de RFC supplémentaire** : décision discutée explicitement à l'ouverture du sprint, tracée ici. Une RFC dédiée serait écrite si le format de stockage évolue (schema_version bump, migration nécessaire) ou si on bascule sur IndexedDB.

Le port `ProgressRepository` lui-même n'est pas touché : il existait déjà depuis le Lot 0. On ne fait qu'écrire son premier adapter.

## Ce qui a été fait

### Bibliothèque SRS pure (`src/lib/srs/`)

- **`sm2.ts`** — `applyReview(state | null, quality, today): SrsState`. Formule SM-2 standard, ease minoré à 1.3, premier rappel → interval=1 si succès / 0 si échec, deuxième succès → interval=6, suivants `interval * ease`. Pure, déterministe : `today` est explicite. 9 tests.
- **`quality.ts`** — `qualityFromSession({refusals, completed}): 0..5`. Barème :
  - 0 refus → 5, 1 refus → 4, 2 refus → 3 (limite succès/échec), 3-4 → 2, 5+ → 1, non complété → 0. 6 tests.
- **`dueQueue.ts`** — `isDue`, `countDue`, `pickNextDue`. Tri : due plus ancienne d'abord, puis moins de successes, puis ordre d'insertion. 8 tests.

### Persistance (`src/adapters/storage/`)

- **`LocalStorageProgressRepository.ts`** — implémente le port `ProgressRepository` (Lot 0). Blob JSON sous `sinogrammes:progress`, `schema_version: 1`. Validation : versions inconnues et JSON corrompu retombent sur `[]`. 9 tests.

### Renderer port + Hanzi Writer (`src/domain/ports/`, `src/adapters/renderer/`)

- **`CharacterRenderer`** étendu avec `setOnComplete(callback): () => unregister`. Le port autorise plusieurs callbacks via un Set (utile si on en a besoin plus tard pour stats / log).
- **`HanziWriterRenderer.setOnComplete`** implémenté en câblant le `onComplete` de la `QuizOptions` de Hanzi Writer. Les erreurs dans les callbacks sont attrapées et loguées sans faire planter le renderer.

### Canvas (`src/features/canvas/Canvas.tsx`)

- Compteur de **refus authentiques** dans une `useRef` (pas de re-render à chaque incrément). Un `repeated_stroke` (synthétisé côté UI) ne compte pas comme refus.
- Émission de `onCharacterCompleted({refusals, completed: true})` quand Hanzi Writer signale la fin du quiz. Garde-fou `completionFiredRef` pour ne pas émettre plusieurs fois la même session.
- Reset au changement de hanzi et au `resetAll` (Tout effacer ouvre une nouvelle session).
- Couverture : 5 tests sur `onCharacterCompleted` (succès, refus comptés, repeat ignoré, reset, anti-doublon, ré-émission après Tout effacer).

### Hook + App

- **`src/features/progress/useProgress.ts`** — charge la liste au mount via le `ProgressRepository`, expose `entries` (réactif) et `recordSession(ref, session, today?)` qui applique SM-2 + persiste + met à jour `entries`. Repo injectable pour les tests. 5 tests d'intégration (création, cumul, abandon, persistance reload).
- **`App.tsx`** — charge `characters`/`words` du bundle pour résoudre `hanzi → entryId` et `entryId → hanzi`. Reçoit `onCharacterCompleted` du Canvas, résout le `Character` par hanzi, appelle `recordSession`. **Bouton "Réviser (N)"** dans le header de la vue glossaire, désactivé si N=0, clique → `pickNextDue` → ouvre la vue practice avec ce caractère.

### i18n FR/EN

- Section `review.button_*` avec pluralisation (`zero`, `one`, `other`).
- Footer mis à jour : "Lot 3 — Révision (sprint 1)".

### Tests E2E (`e2e/srs-review.spec.ts`)

Compléter un vrai caractère via Pointer Events serait fragile (il faudrait tracer N traits exacts). On vérifie plutôt la chaîne **persistance → file → bouton Réviser** en pré-seedant `localStorage` :

- Réviser désactivé sans progression.
- Compteur reflète le nombre d'items dus.
- Cliquer ouvre le canvas sur le caractère le plus en retard.
- Compteur survit à un reload.

La complétion réelle (Hanzi Writer → onComplete → SM-2) est couverte exhaustivement par les tests unitaires Canvas + useProgress.

## Notes / surprises

- Le format de date stocké est ISO 8601 sans heure (`YYYY-MM-DD`). Comparaison lexicographique = correcte pour ce format. Évite les bagarres de fuseau horaire.
- L'ordre `update ease puis compute interval` vs `compute interval avec old ease puis update ease` n'est pas universellement standardisé dans SM-2 (Wikipedia fait l'un, le papier original l'autre, Anki encore autre). On a choisi la première forme (utilise le nouveau ease). Effet : intervalles très légèrement plus grands. Pour mono-utilisateur l'écart est négligeable.
- Le bouton Réviser est dans le header (à côté du toggle de langue) plutôt que dans le glossaire — pour rester visible/accessible quoi qu'il arrive. Caché pendant la vue practice/detail pour éviter de distraire pendant le tracé.
- L'unité de progression actuelle est **le caractère uniquement**. Les mots ne sont pas tracés en propre dans le Lot 1-2 ; les ajouter à la file SRS demanderait une UX dédiée (tracé séquentiel des caractères constitutifs ?), reportable.
